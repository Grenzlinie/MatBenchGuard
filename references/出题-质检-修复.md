# 质检

## 判断题目是否真正属于生物领域

审查首先判断题目是否真正涉及：

- 生物对象，如基因、蛋白、细胞、组织、物种、通路或表型；

- 生物数据，如测序数据、表达矩阵、变异、蛋白结构或代谢网络；

- 生物分析过程，如比对、注释、建模、统计检验或功能预测；

- 生物学终点，如差异基因、细胞类型、候选靶点、代谢通量或蛋白功能；

- 必要的生物学或生物信息学知识。

题目会被分类为：

- `BIO_CORE`：核心目标是解决生物学问题；

- `BIO_METHOD`：主要考察计算方法，但正确性依赖领域知识；

- `BIO_WRAPPER`：包含生物名词，但实质只是通用文件处理；

- `NON_BIO`：不属于生物任务；

- `AMBIGUOUS`：信息不足，暂时无法明确判断。

同时，Skill 会提取题目声称考察的能力，并检查：

```Plain Text
目标能力
→ 必须执行的科学操作
→ 应产生的结果
→ Checker 实际评分内容
```

如果题目声称考察代谢模型重建，但只提交几个论文中的数值就可以获得满分，则会被判定为能力目标与评分机制不一致。

---

## 验证数据、模型和软件是否真实可用

Skill 会检查题目依赖的资源是否真实存在，并且能够被 Agent 自动访问。

审查范围包括：

- GEO、SRA、NCBI、ENCODE、PDB、UniProt 等 accession；

- 数据集下载链接；

- 论文补充数据；

- 预训练模型与 tokenizer；

- 参考基因组与注释文件；

- Python、R、conda 和系统软件包；

- Docker、依赖锁定文件和外部求解器；

- 商业数据库、受控数据和需要授权的资源。

资源审查不仅检查网站首页是否能够打开，还会验证到：

- accession 是否存在；

- 是否公开；

- 具体文件是否能够下载；

- 下载内容是否为真实数据；

- 物种、样本、实验条件和版本是否匹配；

- 文件大小、checksum 和样本数量是否合理；

- 在实际 benchmark 环境中是否能够访问。

例如，数据库主页返回 HTTP 200，并不能证明完成题目所需的具体数据可以获得。

资源会根据重要性标记为：

- `CRITICAL`：不可替代的核心资源；

- `REPLACEABLE`：允许使用稳定镜像或等价来源；

- `OPTIONAL`：缺失不会阻止任务完成。

网络错误也会区分为临时故障、限流、权限问题、文件消失和资源身份不匹配，避免将短暂网络异常直接判定为题目失效。

---

## 检查题目设计是否完整、自洽

Skill 会交叉检查题包中的：

- instruction；

- steps 或 workflow；

- manifest；

- task 配置；

- resources；

- grading specification；

- checker；

- environment 配置。

重点判断：

- 输入和输出是否明确；

- 文件名、字段和路径是否一致；

- 物种、样本、参考版本和单位是否明确；

- 是否缺少必要数据、参数或辅助文件；

- 任务步骤是否覆盖全部目标；

- 是否存在循环依赖或无法执行的顺序；

- 是否明确区分必须、推荐、允许和禁止的操作；

- 是否允许联网、安装软件或调用外部 API；

- 是否允许使用等价工具；

- 输出格式、排序、去重和缺失值规则是否明确。

此外，还会判断题目是否存在信息不足但要求唯一答案的情况。例如，一个代谢网络可能存在多种合理的 gap\-filling 方案，如果题目没有规定约束条件，却只接受一个固定模型，则可能并不是一个公平的 benchmark。

---

## 检查数据是否能够回答题目

数据可下载并不代表数据足以支持任务。

Skill 会进一步检查：

- 样本数量是否足够；

- 是否存在必要对照；

- 分组标签是否完整；

- 生物学分析单位是否正确；

- 是否存在伪重复；

- 训练、验证和测试是否独立；

- 是否混用了不同物种、基因组版本或注释版本；

- 是否缺少参考基因组、sample sheet、模型权重或人工整理结果；

- 给定数据能否支持题目要求的科学结论。

还会针对不同生物任务检查潜在泄漏，例如：

- 蛋白序列高相似度泄漏；

- 同一患者同时出现在训练集和测试集；

- 同一 donor 或 cell line 跨集合出现；

- 药物 scaffold 泄漏；

- 同一研究队列或样本来源泄漏；

- 相同或近重复结构进入不同数据划分。

---

## 审查 Checker 是否真正评价科学任务

Checker 是整个 benchmark 最关键的部分。

Skill 会建立以下映射：

```Plain Text
Instruction 要求
→ Agent 必须完成的工作
→ 产生的核心输出
→ Checker 实际读取
→ Checker 实际计分
```

重点检查：

- 核心输出是否被读取；

- 关键中间结果是否有可验证证据；

- Checker 是否只检查文件存在；

- Checker 是否只比较少量硬编码数值；

- 是否忽略模型文件、预测结果或关键日志；

- 所有评分项是否真正影响最终分数；

- 是否存在 always\-pass、always\-zero、除零或方向反转；

- 正确结果是否能够获得高分；

- 生物学错误但格式正确的答案是否可能通过。

如果 instruction 要求构建完整模型，但 Checker 完全不读取模型，只检查几个数字，则会被判定为严重缺陷。

---

## 动态测试 Checker 的鲁棒性

除了阅读 Checker 代码，Skill 还会构造不同类型的提交并实际运行评分。

测试包括：

- 缺失输出；

- 空文件；

- 错误格式；

- 随机答案；

- 常数答案；

- 全正或全负预测；

- 重复记录；

- 冲突记录；

- 大量无关记录；

- `NaN`、`Inf` 和极端数值；

- 仅提交少量 Gold 数值；

- 省略核心模型或结果文件；

- 阈值边界输入；

- 能够覆盖全部区域的投机答案。

对于不同任务，还会使用领域专用攻击：

- BED：全染色体 mega\-peak；

- VCF：坐标偏移和 REF/ALT 错误；

- 单细胞：细胞顺序变化、全零矩阵和 donor 泄漏；

- 蛋白：非法氨基酸、长度错配和同源泄漏；

- 代谢模型：缺失模型、错误 objective 和 gene/reaction 混淆。

---

## 检查评分是否具有区分度

一个 Checker 不仅要防止错误答案骗分，还应当能够合理区分不同质量的答案。

Skill 会构造多个质量等级，例如：

- 0% 正确；

- 10% 正确；

- 30% 正确；

- 50% 正确；

- 80% 正确；

- 100% 正确。

然后检查：

- **单调性**：更好的答案不能获得更低分；

- **灵敏度**：答案有明显改善时，得分也应变化；

- **饱和性**：不同质量答案不能都接近满分；

- **特异性**：格式正确但科学错误的答案应得低分；

- **局部贡献**：某个简单字段不能决定全部分数。

Skill 还会执行变形测试，验证语义等价但文件表示不同的答案是否得到一致评分。

例如，改变记录顺序、反应顺序或无关 metadata，不应改变科学结果的得分。

---

## 判断 Gold Standard 是否可信

Skill 会审查 Gold Standard 的来源和质量，包括：

- 是否来自真实实验；

- 是否由专家人工整理；

- 是否来自论文正文或补充材料；

- 是否由某个计算工具生成；

- 是否通过图表数字化获得；

- 是否存在测量误差或标注不确定性；

- 是否独立于被评价的方法；

- 评分容差是否有科学依据。

如果 Gold 只是某个软件的输出，那么它更适合衡量“与该软件的一致性”，不一定能代表真正的生物学正确性。

对于可能存在多个合理答案的任务，Skill 会判断 Checker 是否支持：

- 数值容差；

- 集合级匹配；

- 排名评价；

- 证据链评价；

- 多个可接受解。

---

## 支持两种论文审查模式

### 无需查看原文模式

用于快速筛查题包是否能够独立成立。

主要检查：

- 是否为真正的生物题；

- 数据和软件是否可获得；

- instruction 是否完整；

- Checker 是否合理；

- 是否存在 gaming、泄漏和执行风险。

该模式不会声称题目与论文完全一致。

### 需要查看原文模式

在基础审查之外，进一步阅读论文正文、Methods、图表和补充材料。

检查：

- instruction 是否忠实于论文方法；

- 数据、样本和实验条件是否一致；

- 参数和软件版本是否一致；

- Gold 是否真正来自论文；

- 是否遗漏人工整理或补充模型；

- 当前数据库版本是否能够复现历史结果；

- 正确执行论文流程后是否能够获得高分。

同时区分：

- `EXACT_REPRODUCTION`：严格复现论文；

- `METHOD_REIMPLEMENTATION`：允许等价实现；

- `SCIENTIFIC_EXTENSION`：在论文基础上进行新分析。

科学扩展任务不应使用论文中的精确结果作为唯一 Gold。

---

## 支持不同执行深度

审查可以按资源和需求选择执行级别：

- `E0 STATIC`：文件、代码和语义静态检查；

- `E1 CHECKER_DYNAMIC`：运行 Checker 攻击测试；

- `E2 SMOKE_RUN`：使用最小输入验证流程可以启动；

- `E3 REDUCED_REPRODUCTION`：使用缩小数据运行完整流程；

- `E4 FULL_REPRODUCTION`：使用完整数据和环境复现任务。

只有完成 `E3` 或 `E4`，才能声称科学流程经过真实运行验证。

---

## 固定输出审查报告

审查结束后，所有结果都会写入题包根目录：

```Plain Text
benchmark_audit/
```

主要文件包括：

```Plain Text
benchmark_audit/
├── audit_report.md
├── audit_report.json
├── findings.jsonl
├── resource_checks.json
├── checker_tests.json
├── audit_manifest.json
├── evidence/
├── logs/
└── patches/
```

其中：

- `audit_report.md`：供人工阅读的完整报告；

- `audit_report.json`：供程序汇总的结构化结果；

- `findings.jsonl`：逐条记录所有问题；

- `resource_checks.json`：保存数据和软件可达性结果；

- `checker_tests.json`：保存动态攻击和单调性测试；

- `audit_manifest.json`：记录输入输出文件和哈希；

- `evidence/`：保存脚本输出和测试证据；

- `patches/`：保存建议修改补丁。

已有审查结果不会被直接覆盖，而会归档到：

```Plain Text
benchmark_audit_history/<audit_id>/
```

便于比较修复前后的变化。

---

## 最终结论

最终审查结论分为：

- `PASS`：题目可以直接进入 benchmark；

- `CONDITIONAL`：存在可修复问题，需要修改后复审；

- `REJECT`：存在根本性问题，不适合使用；

- `NOT_ASSESSABLE`：关键证据不足，无法可靠判断。

所有问题按照严重程度分为：

- `FATAL`

- `HIGH`

- `MEDIUM`

- `LOW`

每个问题都会提供：

- 受影响文件和位置；

- 观察到的事实；

- 证据；

- 科学或技术影响；

- 可能的失败或投机场景；

- 最小修复方法；

- 修复后的复测方案

# 修复

`BioMaster Benchmark Repair` 是一个用于自动修复生物学、生物医学和生物信息学 benchmark 题包的 Skill。它读取审查结果，根据已发现的问题修改题包、运行回归测试并重新审查，形成完整的：

```Plain Text
审查 → 修复 → 测试 → 复审 → 发布或放弃
```

工作闭环。

---

## 读取审查结果并制定修复计划

默认读取题包根目录下的：

```Plain Text
benchmark_audit/
├── audit_report.json
├── findings.jsonl
├── resource_checks.json
├── checker_tests.json
└── audit_manifest.json
```

它会根据每个问题的严重程度、证据、影响和建议修复方法，生成结构化修复计划。

问题被分为三类：

- `AUTO_FIX`：能够确定性自动修复；

- `ASSISTED_FIX`：有充分证据支持，可以生成并应用明确补丁；

- `ABANDON`：缺少可靠依据，或修复会改变核心科学定义。

---

## 修复题包结构和配置

可以自动处理的常见问题包括：

- 文件路径错误；

- instruction、steps、manifest 和 Checker 中的文件名不一致；

- JSON、YAML 或 TOML 格式错误；

- grading 权重异常；

- 输出字段和数据类型不一致；

- 相对路径或工作目录错误；

- 缺失必要配置；

- 输出目录未正确创建。

这类修改通常不会改变题目的科学目标，因此可以在隔离环境中自动完成并测试。

---

## 补充和规范 Instruction

在不改变任务含义的前提下，Skill 可以补充：

- 输入和输出文件；

- 必需字段和数据类型；

- 物种、样本和参考版本；

- 基因、蛋白、转录本或反应 ID 类型；

- 单位、排序和去重规则；

- 缺失值与非法值处理；

- 随机种子和数值容差；

- 是否允许联网、安装软件或使用等价工具；

- REQUIRED、RECOMMENDED、ALLOWED 和 FORBIDDEN 操作。

对于论文或题包中没有依据的生物学参数，不会自行猜测或编造。

---

## 修复数据、软件和环境问题

对于 Auditor 发现的资源问题，Skill 可以：

- 将数据库主页替换为具体 accession；

- 修正失效的官方链接；

- 增加稳定镜像；

- 固定数据和数据库版本；

- 增加 checksum 和文件大小；

- 修正软件包名称和版本；

- 补充系统依赖或外部求解器；

- 增加 lock file 或容器环境；

- 修正明显不合理的时间、内存和存储预算。

如果核心数据需要未提供的权限、已经永久失效，或无法合法获得，则该题会被直接放弃。

---

## 修复 Checker 的覆盖和评分问题

`BioMaster Benchmark Repair` 会重点修复影响 benchmark 公平性的 Checker 缺陷，例如：

- 没有读取 instruction 要求的核心输出；

- 缺失模型或结果文件仍能获得高分；

- 只比较几个硬编码数值；

- 空文件或错误格式导致崩溃；

- `NaN`、`Inf` 或极端值绕过判断；

- 重复记录异常抬高分数；

- 分数方向写反；

- 某些评分项没有进入最终 reward；

- 文件顺序或无关 metadata 影响评分；

- 随机、常数或最小投机答案也能通过；

- 更好的答案反而获得更低分。

每次修改 Checker，都必须增加对应的回归测试。

---

## 在隔离工作区中安全修复

Skill 不会直接在原始题包上边改边试。

所有修改首先进入隔离目录：

```Plain Text
<benchmark_root>/.benchmark_repair_tmp/<repair_id>/
```

随后依次运行：

- 文件和格式检查；

- 路径与 Schema 检查；

- Checker 静态检查；

- 动态攻击测试；

- 单调性测试；

- 变形测试；

- 必要的 smoke test 或缩小流程测试；

- 修复后的 Auditor 复审。

只有测试通过后，修改才会正式写回题包。

如果测试失败，则停止修改并回滚，避免留下半修复状态。

---

## 无法可靠修复时直接放弃

`BioMaster Benchmark Repair` 不要求修复所有题目。

出现以下情况时，会停止修复并标记为 `ABANDONED`：

- 题目不是真正的生物或生信任务；

- 不可替代的核心数据永久不可达；

- Gold Standard 来源无法验证；

- Gold 与论文或真实任务明显冲突；

- 缺少无法恢复的人工整理结果、模型或历史数据库；

- 修复需要猜测关键生物学参数；

- 多个合理答案无法建立公平评分方法；

- Checker 必须重新定义任务才能修复；

- 声明资源下无法完成计算；

- 修复后仍然存在 FATAL 问题；

- 同一个根本问题经过两次尝试仍未解决。

Skill 不会通过以下方式强行获得 PASS：

- 将答案写入 instruction；

- 复制论文中的 Gold 数值；

- 读取 solution 或隐藏答案；

- 随意降低评分阈值；

- 删除核心科学步骤；

- 伪造数据、参数或证据。

---

## 修复后自动重新审查

修改完成后，Skill 必须重新运行 `BioMaster Benchmark Auditor`，比较修复前后的：

- 最终 verdict；

- 加权分数；

- Hard Gate；

- FATAL、HIGH、MEDIUM 和 LOW 问题数量；

- 数据资源可达等级；

- Checker 动态攻击结果；

- 评分单调性；

- 未解决问题；

- 新引入的问题。

最终状态包括：

- `REPAIRED`：修复完成，复审为 PASS；

- `PARTIALLY_REPAIRED`：不存在 FATAL，但仍有非致命问题；

- `ABANDONED`：存在无法可靠修复的根本问题；

- `ROLLED_BACK`：修复失败，已恢复原始题包。

---

```Plain Text
├── logs/
└── repair_manifest.json
```

其中：

- `repair_summary.md`：供人工阅读的修复报告；

- `repair_report.json`：机器可读的修复结果；

- `repair_plan.md`：修复前的计划；

- `changes.jsonl`：逐条记录文件修改；

- `regression_tests.json`：保存回归测试结果；

- `re_audit_comparison.json`：比较修复前后的审查结果；

- `patches/`：保存已应用或建议的补丁；

- `repair_manifest.json`：保存哈希和修复历史。

旧结果会归档到：

```Plain Text
benchmark_repair_history/<repair_id>/
```
