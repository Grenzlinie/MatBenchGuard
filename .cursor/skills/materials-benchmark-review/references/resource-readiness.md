# Data, model, software, and environment readiness

For each category record `READY`, `NOT_REQUIRED`, `NOT_READY`, or
`NOT_ASSESSABLE`:

- `data`: datasets, structures, tables, annotations, splits, references;
- `model`: pretrained models, weights, potentials, tokenizers, checkpoints;
- `software`: indispensable software/service and permitted equivalents;
- `environment`: dependencies, versions, hardware/runtime assumptions;
- `license_access`: authentication, permission, license, privacy, consent.

Criterion 2.8 passes only when all five are `READY` or `NOT_REQUIRED`.

For every required object verify role, exact identity/version, embedded path or
locator, actual artifact availability, sufficiency, checksum when available,
license/access, and allowed equivalent. A homepage HTTP 200 is not artifact
access. Retry transient DNS/TLS/timeout/rate-limit failures.

Required external data, pretrained weights, potentials, tokenizers, and
checkpoints must be ready. A model/structure/trajectory explicitly meant to be
trained or generated by the solver is an output, not a prerequisite. Routine
solver parameters are governed by `paper-grounded-audit.md`, not resource
readiness.

A permanently unavailable, authorization/license-gated, identity-mismatched,
or insufficient indispensable input without an allowed equivalent triggers
`INDISPENSABLE_DIRECT_INPUT_UNAVAILABLE`. Transient audit-host failure is
`NOT_ASSESSABLE`, not rejection.

Evaluate filesystem locations according to the declared container layout and
mounts. Missing host paths or a helper's inability to rewrite container paths
are `AUTOMATION_LIMITATION`; they do not make a resource unavailable without
evidence that the declared in-container resource or mount is also invalid.
